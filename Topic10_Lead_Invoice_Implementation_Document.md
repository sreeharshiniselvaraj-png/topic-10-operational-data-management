# Topic 10 – Operational Data Management with Google Sheets
## Implementation Document: Lead and Invoice Status Tracking

**Platform:** n8n v2.40.7  
**Main workflow:** Topic 10 - Lead and Invoice Status Tracking  
**Mock data service:** Topic 10 - Lead Tracking Mock Sheets Server  
**Implementation approach:** Mock Google Sheets service using n8n workflow static data  
**Execution mode:** Manual workflow execution

---

## 1. Objective

This workflow demonstrates a lead-processing lifecycle in which only records with `lead_status` equal to `Pending` are processed. Each selected lead is marked `Processing` before invoice processing. The lead is then marked `Completed` when processing succeeds or `Failed` when processing fails. Operational fields are written back to the corresponding lead record.

The implementation uses a mock Sheets service rather than a live Google Sheets connection. The invoice failure path is simulated in a Code node rather than generated by a live invoice API.

## 2. Architecture Overview

The solution contains two n8n workflows:

1. **Main workflow – Topic 10 - Lead and Invoice Status Tracking**
   - Reads lead records.
   - Filters Pending leads.
   - Processes leads sequentially.
   - Writes Processing, Completed, or Failed status updates.
   - Records execution and error information.

2. **Mock server workflow – Topic 10 - Lead Tracking Mock Sheets Server**
   - Provides GET and PUT webhook endpoints.
   - Stores mock lead rows in n8n workflow static data.
   - Returns lead records and updates a record matched by `lead_id`.

### Mock endpoint

| Method | Endpoint path | Purpose |
|---|---|---|
| GET | `/webhook/mock/sheets/leads-topic10` | Retrieve lead records |
| PUT | `/webhook/mock/sheets/leads-topic10` | Update a lead record matched by `lead_id` |

**Data-store limitation:** The mock server uses n8n workflow static data. It is not a live Google Sheets spreadsheet or Google Sheets API integration.

## 3. Lead Record Structure

The mock lead records contain these fields:

| Field | Purpose |
|---|---|
| `lead_id` | Unique key used to identify the lead |
| `lead_status` | Processing state: Pending, Processing, Completed, or Failed |
| `created_at` | Record creation timestamp |
| `updated_at` | Timestamp of the latest status update |
| `execution_id` | n8n execution ID associated with processing |
| `error_details` | Error description when processing fails |

The sample records are L-101, L-102, and L-103.

## 4. Main Workflow Nodes and Their Purposes

| Node | Node type | Purpose |
|---|---|---|
| `Manual Trigger` | Manual Trigger | Starts the workflow manually |
| `HTTP_GetLeadRecords` | HTTP Request | Calls the mock GET endpoint to retrieve lead rows |
| `Code_FilterPendingLeads` | Code | Keeps only records where `lead_status` is exactly `Pending` |
| `Loop Over Items` | Loop Over Items | Processes pending leads sequentially, one item per loop |
| `HTTP_MarkLeadProcessing` | HTTP Request | Updates the matching lead to Processing and writes execution ID and timestamp |
| `Code_ProcessInvoice` | Code | Simulates invoice processing and returns a success or failure result |
| `IF_InvoiceSuccess` | IF | Routes the result based on whether the status code is 200 |
| `HTTP_MarkLeadCompleted` | HTTP Request | Updates the matching lead to Completed and clears error details |
| `HTTP_MarkLeadFailed` | HTTP Request | Updates the matching lead to Failed and writes the error details |

The Completed and Failed update paths return to the Loop Over Items node so the next pending lead can be processed. The loop's Done output is not connected to another processing node.

## 5. Workflow Execution Sequence

1. `Manual Trigger` starts the workflow.
2. `HTTP_GetLeadRecords` retrieves all lead records from the mock server.
3. `Code_FilterPendingLeads` filters the records and emits only Pending leads.
4. `Loop Over Items` passes one pending lead at a time into the processing path.
5. `HTTP_MarkLeadProcessing` updates that lead to Processing, records `$execution.id`, and writes the current timestamp.
6. `Code_ProcessInvoice` simulates invoice processing.
7. `IF_InvoiceSuccess` checks whether `statusCode` equals 200.
8. On the true branch, `HTTP_MarkLeadCompleted` writes Completed, the execution ID, the update timestamp, and an empty error detail.
9. On the false branch, `HTTP_MarkLeadFailed` writes Failed, the execution ID, the update timestamp, and the error message.
10. Each status-update branch returns to the loop to process the next pending lead.

If no Pending records are returned by the filter, no lead enters the loop and no downstream status update occurs.

## 6. Status Transition Rules

| Processing outcome | Status transition | Write-back behavior |
|---|---|---|
| Invoice processing succeeds | Pending → Processing → Completed | Write `execution_id` and `updated_at`; clear `error_details` |
| Invoice processing fails | Pending → Processing → Failed | Write `execution_id`, `updated_at`, and the error message |
| Lead is not Pending | No transition | Do not process or write back the record |

## 7. Key-Based Update and Sequential Processing

The mock server's update Code node searches for the target record using `lead_id`:

```javascript
const lead = store.leads.find(
  item => item.lead_id === body.lead_id
);
```

If no matching lead is found, the update throws an error rather than updating another record. The main workflow uses Loop Over Items with batch size 1 to process pending leads sequentially.

This demonstrates key-based record targeting and sequential processing. It is not a concurrent-update stress test or production-grade transaction lock.

## 8. Error-Handling Demonstration

The `Code_ProcessInvoice` node simulates a failure for lead L-102 by returning:

- `invoiceStatus`: `FAILED`
- `statusCode`: `500`
- `message`: `500 - Internal Server Error`

The IF node routes this result to `HTTP_MarkLeadFailed`, which writes the Failed status and error message to the matching lead record.

**Test limitation:** This demonstrates the workflow's failure-handling and write-back path. It does not demonstrate an actual HTTP invoice endpoint returning HTTP 500, because the failure is simulated in a Code node.

## 10. Implementation Limitations

- The data service is a mock built with n8n workflow static data, not a live Google Sheets integration.
- Invoice processing is simulated in a Code node, not performed by a live external invoice API.
- The workflow is manually triggered for demonstration.
- Sequential processing is implemented using Loop Over Items with batch size 1.
- The demonstrated key isolation is functional sequential behavior, not a concurrent collision or load test.
- The workflow demonstrates the requested status and audit-field behavior within the mock environment.

## 11. Conclusion

The workflow demonstrates reading lead records, filtering Pending records, marking a lead Processing before invoice handling, and writing Completed or Failed outcomes with execution and timestamp information. Updates target records by `lead_id`, and pending leads are processed sequentially. The implementation uses a mock Sheets service and simulated invoice processing; these limitations should be stated during trainer demonstration.
