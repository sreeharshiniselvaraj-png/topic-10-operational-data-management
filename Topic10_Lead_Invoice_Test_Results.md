# Topic 10: Lead and Invoice Status Tracking

## Test Results Document

**Main workflow:** `Topic 10 - Lead and Invoice Status Tracking`\
**Mock server:** `Topic 10 - Lead Tracking Mock Sheets Server`\
**Test execution reference:** `716026` for the mixed success/failure
run\
**Test status:** All five listed cases marked PASS, with
implementation-scope notes below.

## 1. Test Environment

-   n8n workflow automation environment.
-   Mock Sheets Server using workflow static data.
-   GET and PUT webhook endpoints for lead records.
-   Main workflow uses a Loop Over Items node with Batch Size 1.
-   Invoice processing is simulated in a Code node; no live invoice API
    is called.

## 2. Test Data and Results

### TC-001 --- Success Pipeline Status Transition

**Objective:** Verify that a Pending lead is marked Processing before
invoice processing and then Completed after a successful result.

**Test evidence:** In execution `716026`, L-101 was updated to
`Completed`. The stored record included an `updated_at` timestamp and
execution ID `716026`.

**Expected:** Pending → Processing → Completed, with timestamp and
execution ID recorded.

**Actual:** L-101 finished as Completed; stored audit fields were
populated.

**Result: PASS**

### TC-002 --- Filter Out Non-Pending Records

**Objective:** Verify that Completed and Failed records are not sent to
invoice processing.

**Starting data:** - L-101 --- Completed - L-102 --- Failed - L-103 ---
Completed

**Test evidence:** `Code_FilterPendingLeads` displayed "No output data
returned." This is the expected zero-item result because there were no
Pending records. A subsequent GET request showed that all three statuses
remained unchanged.

**Expected:** Zero items pass the filter and no downstream write-back
occurs.

**Actual:** Zero items were returned; stored statuses remained
Completed, Failed, and Completed.

**Result: PASS**

### TC-003 --- Downstream Error Trap and Log Write

**Objective:** Verify that a failed invoice-processing result is
recorded as Failed with error details.

**Test evidence:** In execution `716026`, L-102 finished with status
`Failed` and `error_details` equal to `500 - Internal Server Error`. The
record also contained the execution ID and updated timestamp.

**Expected:** Pending → Processing → Failed; error details and timestamp
are saved.

**Actual:** L-102 finished as Failed and the expected error text was
persisted.

**Result: PASS --- simulated failure path**

**Scope note:** The failure was generated by the `Code_ProcessInvoice`
simulation. A real downstream HTTP endpoint returning HTTP 500 has not
been tested in this implementation.

### TC-004 --- Execution ID Audit Verification

**Objective:** Verify that the execution ID written to each lead matches
the actual n8n execution.

**Test evidence:** The n8n execution details showed ID `716026`. The
stored records for L-101, L-102, and L-103 each contained
`execution_id: "716026"`.

**Expected:** Stored execution ID matches the n8n execution ID exactly.

**Actual:** Exact match confirmed for all three records.

**Result: PASS**

### TC-005 --- Update Collision Protection (Key Isolation)

**Objective:** Verify that updates target the selected lead using
`lead_id` and do not change unrelated records.

**Test evidence:** During the mixed-outcome run, L-101 and L-103
finished as Completed, while L-102 finished as Failed. The subsequent
GET response returned the same three records and values. The mock update
code finds a record using `item.lead_id === body.lead_id`.

**Expected:** Only the targeted lead is updated; other records remain
unchanged.

**Actual:** The three-lead sequential run preserved each lead's own
status and audit details.

**Result: PASS --- key isolation verified in the tested run**

**Scope note:** This was a sequential functional test using Loop Over
Items with Batch Size 1. It was not a concurrent-update or high-load
stress test.

## 5. Limitations and Follow-up

1.  The data store is an n8n mock server using workflow static data, not
    a live Google Sheets spreadsheet.
2.  Invoice processing is simulated with a Code node, not a live
    downstream API.
3.  TC-003 validates the simulated failure route, not an actual HTTP 500
    response from an external service.
4.  TC-005 validates key-based updates in a sequential run; a separate
    concurrency stress test has not been performed.

These limitations should be disclosed during the trainer demonstration.
